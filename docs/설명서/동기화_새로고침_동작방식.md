## 1. 용어 정의

- **Sources 새로고침**: Sources 화면의 원형 화살표 버튼이 실행하는 프로젝트 파일 재스캔이다.
- **Auto-Watch / project file sync**: Rust `notify::RecommendedWatcher`로 프로젝트 폴더를 재귀 감시하고, 스냅샷과 파일 hash를 비교해 created/modified/deleted task를 만드는 기능이다.
- **dataVersion**: 파일 변화 후 증가시키는 프런트엔드 버전 값이다. 그래프처럼 파생 데이터를 캐시하는 화면이 이를 보고 다시 계산한다.
- **앱 write 무시 구간**: 앱이 직접 쓴 파일은 4초 동안 watcher의 외부 변경 처리에서 제외한다. 앱 자신의 저장을 외부 변경으로 다시 처리하는 루프를 막기 위한 것이다.

코드 근거: `src-tauri/src/commands/file_sync.rs`, `src/lib/project-file-sync.ts`, `src/stores/wiki-store.ts`.

## 2. 새로고침 기능의 위치와 동작

### 2.1 화면 위치

수동 프로젝트 파일 새로고침은 왼쪽 사이드바의 **Sources 화면 상단 오른쪽**에 있다.

- 아이콘: `RefreshCw` 원형 화살표
- 위치: Sources 제목 오른쪽, Import 및 Folder 버튼 왼쪽
- 접근성 라벨: `Refresh folder`
- tooltip 설명: source folder를 다시 스캔하고 새 파일·수정 파일은 ingest queue, 삭제 파일은 wiki/index 정리 후 파일 트리를 재구성

코드 근거: `src/components/sources/sources-view.tsx`, `src/i18n/en.json`.

설정 화면의 업데이트 확인, embedding 통계 등에도 원형 화살표가 있으나 이 문서의 프로젝트 동기화 새로고침과는 별개다.

### 2.2 버튼을 누르면 실행되는 흐름

```text
Sources Refresh
  → rescanProjectFileSync()
  → Rust rescan_project_files()
  → 프로젝트 감시 대상 전체와 .llm-wiki/file-snapshot.json 비교
  → created / modified / deleted task 처리
  → 삭제 cleanup + raw source ingest 등록
  → 프로젝트 루트 파일 트리 재구축
  → dataVersion 증가
  → 변경 목록에 현재 열린 파일이 있으면 그 파일 본문 재읽기
  → Sources 자체 목록(raw/sources)도 다시 로드
```

수동 스캔 대상은 `raw/sources`만이 아니다. 다음을 포함한다.

- 허용 규칙을 통과한 `raw/sources/**`
- `wiki/**/*.md`
- 루트 `purpose.md`
- 루트 `schema.md`

다음은 제외된다.

- `.llm-wiki/**`
- `wiki/media/**`
- `.DS_Store`, `Thumbs.db`, `desktop.ini`
- 설정의 제외 디렉터리/glob
- `raw/sources`의 제외 확장자, 비허용 확장자, 최대 크기 초과 파일

코드 근거: `src-tauri/src/commands/file_sync.rs`의 `enqueue_rescan_changes()`, `should_watch_rel()`, `relative_watch_path()`.

### 2.3 현재 열린 파일과 파일 트리

- **전체 파일 트리**: 변경 유무와 관계없이 `listDirectory(project root)`로 다시 읽어 `fileTree`를 교체한다.
- **Sources 목록**: 버튼 핸들러의 `finally`에서 `loadSources()`가 `raw/sources`를 다시 읽는다.
- **현재 열린 파일**: rescan이 반환한 변경 task의 상대 경로 목록에 현재 `selectedFile`이 포함될 때만 디스크에서 다시 읽는다.
- 변경 task가 하나도 없는 단순 새로고침은 `relativePaths=[]`로 호출되므로, 현재 열린 파일을 무조건 강제 재읽기하는 버튼은 아니다.
- 변경 파일이 삭제됐거나 읽기에 실패하면 선택을 해제하고 `fileContent`를 비운다.

따라서 이 버튼은 “현재 문서만 reload”가 아니라 **전체 감시 대상 재스캔 + 전체 트리 갱신**이며, 열린 문서 reload는 실제 변경으로 판정된 경우에만 부가적으로 수행한다.

코드 근거: `src/lib/project-file-sync.ts`의 `rescanProjectFileSync()`, `refreshAfterFileChanges()`, `src/components/sources/sources-view.tsx`.

### 2.4 그래프와 Insights 재계산

파일 change batch 처리 뒤 `dataVersion`을 1 증가시킨다. Graph 화면은 이 값이 직전에 읽은 값과 다르면 `buildWikiGraph()`를 다시 실행하고, 그 결과로 다음을 모두 다시 계산한다.

- 노드와 edge
- Louvain communities와 cohesion
- Surprising Connections
- Knowledge Gaps

Graph 화면이 현재 mount되어 있지 않다면 다음 표시 시 최신 `dataVersion`을 기준으로 로드된다. 즉 Sources 새로고침에서 그래프 함수를 직접 부르는 것은 아니지만, **dataVersion invalidation을 통해 그래프와 Insights가 다시 계산**된다.

코드 근거: `src/components/graph/graph-view.tsx`, `src/lib/wiki-graph.ts`, `src/lib/project-file-sync.ts`.

## 3. 새로고침 없는 자동 감지

### 3.1 감시 방식

Source Watch 설정이 enabled이면 프로젝트를 열 때 `startProjectFileSync()`가 실행된다. 백엔드는 다음 방식으로 감시한다.

1. 프로젝트 루트를 `RecursiveMode::Recursive`로 watch
2. `raw/sources`와 `wiki`에도 supplemental recursive watch 등록
3. OS file event를 최대 약 700ms 동안 batch
4. `.llm-wiki/file-snapshot.json`의 기존 hash/size와 현재 파일을 비교
5. created, modified, deleted task 생성
6. `file-sync://changed` event를 프런트엔드에 전달
7. 프런트엔드는 추가 250ms debounce 후 cleanup/ingest/화면 갱신

32MiB 이하 파일은 MD5 hash와 크기를 비교한다. 그보다 큰 파일은 hash가 없으므로 코드의 equality 비교가 주로 크기에 의존한다. mtime은 metadata에 저장되지만 `enqueue_paths()`의 최종 동일성 판단은 hash와 size를 비교한다. 따라서 **32MiB 초과 파일이 동일 크기로 내용만 바뀐 경우 변경을 놓칠 가능성이 코드상 존재**한다.

Linux에서는 notify event 보완을 위해 10초 주기의 periodic rescan이 있지만, macOS/Windows에는 이 Linux 전용 주기 스캔이 없다.

코드 근거: `src-tauri/src/commands/file_sync.rs`.

### 3.2 자동 변경 시 화면 갱신

외부 변경 event가 처리되면 다음이 자동 수행된다.

- 전체 프로젝트 파일 트리 재구축
- `dataVersion` 증가
- 현재 열린 파일이 변경 목록에 있으면 본문 재읽기
- Graph/Insights 캐시 무효화 및 재계산
- raw source의 created/modified라면 설정에 따라 ingest queue 등록
- raw source 또는 wiki page의 deleted라면 관련 cleanup

즉 Auto-Watch가 켜져 있고 OS/Synology 변경 event가 정상 전달되면 일반적으로 수동 Refresh가 필요하지 않다. 다만 watcher event 누락, 설정상 제외 파일, 32MiB 초과 동일 크기 수정 등에는 수동 rescan도 동일한 hash/size 한계를 일부 공유한다.

## 4. Auto-Watch의 수정 감지 범위

### 4.1 `raw/sources` 기존 파일 수정

**감지하며 재인제스트를 등록한다.** 정확한 조건은 다음과 같다.

- source watch `enabled: true`
- `autoIngest: true`
- task 종류가 `created` 또는 `modified`
- 경로가 `raw/sources/` 아래
- ingest 가능한 확장자
- include/exclude/glob/크기 규칙 통과
- usable LLM 설정 존재

수정 여부는 스냅샷의 이전 hash/size와 현재 hash/size로 판정한다. ingest queue에도 자체 cache가 있으므로 실제 파일 내용 hash가 기존 ingest와 같으면 후속 처리에서 skip될 수 있다.

코드 근거: `src/lib/project-file-sync.ts`의 `enqueueRawSourceChanges()`, `src/lib/source-lifecycle.ts`, `src/lib/ingest-cache.ts`.

### 4.2 사람이 직접 수정한 `wiki/entities`, `wiki/concepts` 등

**감지 대상이다.** `should_watch_rel()`은 `wiki/` 아래 모든 `.md`를 허용한다. 감지 후에는:

- 파일 트리 갱신
- 열린 파일이면 내용 재읽기
- `dataVersion` 증가
- 그래프/검색 관련 캐시 무효화

하지만 **자동 ingest 대상은 아니다.** `enqueueRawSourceChanges()`가 `raw/sources/` 경로만 고르기 때문이다. 즉 직접 수정한 wiki page는 화면과 그래프에 반영되지만, 그것을 source처럼 다시 분석해 다른 페이지를 생성하지 않는다.

### 4.3 `wiki/queries/`의 Save to Wiki 파일

`wiki/queries/*.md`도 watcher 경로 규칙상 감지 대상이다. 다만 앱의 `writeFile()`은 대상 경로를 4초 동안 app-write ignore로 표시하므로, 같은 앱이 Save to Wiki로 쓴 직후의 watcher event는 외부 변경 처리에서 제외된다. Save to Wiki 자체 코드가 tree/dataVersion 및 필요한 auto-ingest를 별도로 처리한다.

다른 컴퓨터에서 동기화되어 들어온 `wiki/queries/*.md`는 외부 변경으로 감지되어 트리와 화면/버전은 갱신된다. 그러나 file-sync 경로에는 query를 자동 ingest하는 분기가 없으므로 **외부에서 새로 유입된 query 파일 자체가 Auto-Watch만으로 자동 ingest된다고 볼 수 없다**.

코드 근거: `src-tauri/src/commands/file_sync.rs`의 `mark_app_write_path()`, `should_watch_rel()`, `src/lib/project-file-sync.ts`.

## 5. 메모리 캐시와 외부 변경

### 5.1 파일 트리와 열린 파일

프런트엔드는 Zustand store에 `fileTree`, `selectedFile`, `fileContent`, `dataVersion`을 보관한다. 외부 파일 변경을 감지하면 파일 트리는 디스크에서 다시 만들고, 선택된 파일이 변경 task에 포함됐을 때 `fileContent`를 다시 읽는다.

따라서 “프로젝트를 열 때 한 번 읽은 뒤 영원히 캐시”하는 구조는 아니다. Auto-Watch가 켜져 있으면 외부 변경에 따라 갱신한다. Auto-Watch가 꺼져 있거나 event를 놓치면 Sources Refresh 또는 파일을 다시 선택하는 동작이 필요하다.

### 5.2 편집 중 외부 변경의 위험

편집기는 현재 내용을 메모리에 두고 입력 후 1초 debounce로 디스크에 저장한다. 외부 변경이 감지되면 store의 `fileContent`가 새 디스크 내용으로 교체되어 editor가 새 content prop으로 재생성될 수 있다.

그러나 다음 기능은 코드에 없다.

- unsaved local edit와 incoming external edit의 3-way merge
- 파일을 다시 읽기 전 “외부에서 변경됨” 확인 dialog
- optimistic concurrency용 revision/etag 비교
- dirty 상태를 기준으로 watcher reload를 보류하는 로직

따라서 A가 같은 파일을 편집 중이고 B의 변경이 동기화되면, 타이밍에 따라 A의 미저장 편집이 화면에서 교체되거나 A의 1초 지연 저장이 B의 내용을 다시 덮어쓸 수 있다. 이것은 코드상 보호되지 않은 위험이다.

코드 근거: `src/components/layout/preview-panel.tsx`, `src/components/editor/wiki-editor.tsx`, `src/lib/project-file-sync.ts`.

## 6. 재인제스트와 사람이 수정한 wiki 내용

### 6.1 LLM이 기존 내용을 읽는가

Entity, Concept, Query, Synthesis, Comparison, Source summary 같은 content page가 같은 경로에 이미 있으면, 새 생성 내용을 바로 덮어쓰지 않는다.

1. 기존 파일을 디스크에서 다시 읽는다.
2. `sources`, `tags`, `related` 배열을 union한다.
3. 기존 body와 새 body가 다르면 LLM에 두 버전을 모두 전달해 coherent merge를 요청한다.
4. 결과 body가 기존/신규 중 더 긴 쪽의 70%보다 짧으면 손실 가능성이 있다고 보고 거부한다.
5. 기존 `type`, `title`, `created`를 강제로 보존하고 `updated`를 오늘로 설정한다.

따라서 사람이 직접 추가한 본문은 LLM merge 입력으로 전달되며 **보존을 시도**한다.

### 6.2 보존이 보장되지는 않는 경우

완전한 무손실 보장은 아니다.

- LLM merge 자체가 의미를 잘못 합칠 수 있다.
- 70% length 검사는 큰 삭제만 막는 휴리스틱이다.
- LLM merge 실패/형식 오류/길이 검사 실패 시 backup을 시도한 뒤 fallback으로 `incoming body + array-field union`을 반환한다. 이 fallback은 기존 body를 보존하지 않으므로 수동 본문이 현재 파일에서 사라질 수 있다.
- backup은 best-effort이며 backup 실패도 ingest를 막지 않는다.
- Index와 Overview는 listing page라서 merge하지 않고 전체 overwrite한다.
- Log는 기존 내용 뒤에 append한다.

결론적으로 수동 편집한 Entity/Concept는 일반 overwrite보다 보호가 강하지만, **재인제스트로부터 완전히 안전하지 않다**. 중요한 수동 편집은 Synology version history나 Git 등 별도 이력 보호가 필요하다.

코드 근거: `src/lib/ingest.ts`의 `writeFileBlocks()`, `src/lib/page-merge.ts`.

## 7. 두 컴퓨터의 동시 편집과 Synology 충돌

### 7.1 앱 내부 잠금 범위

ingest에는 프로젝트별 async mutex가 있어 **한 앱 프로세스 안에서** 동시에 실행되는 ingest들을 직렬화한다. 하지만 이 mutex는 TypeScript 메모리의 module-level map이며, A컴퓨터와 B컴퓨터 사이에는 공유되지 않는다.

파일 write도 일반 wiki 저장은 `fs::write` 기반이다. 일부 상태 파일에는 atomic temp-file rename이 있지만, 두 컴퓨터를 조정하는 distributed lock, lock file protocol, compare-and-swap은 없다.

따라서 두 컴퓨터가 같은 Index/Overview/Entity 파일을 동시에 ingest하거나 편집하면 last writer wins 또는 Synology의 충돌 처리 결과에 의존한다.

코드 근거: `src/lib/project-mutex.ts`, `src/lib/ingest.ts`, `src-tauri/src/commands/fs.rs`.

### 7.2 Synology가 같은 경로를 한 버전으로 결정한 경우

앱은 Synology API나 revision 정보를 보지 않는다. 디스크에서 최종적으로 바뀐 파일 하나만 watcher가 modified로 감지해 다시 읽는다. 어떤 컴퓨터의 버전이 선택됐는지, 다른 버전이 유실됐는지는 앱이 판별하지 않는다.

### 7.3 Synology가 별도 “충돌 파일”을 만든 경우

앱에는 `conflict`, `Synology`, 충돌 파일명 패턴을 인식하는 전용 코드가 없다. 따라서 결과는 충돌 파일의 위치와 확장자에 따라 달라진다.

- `wiki/**` 아래 `.md` 충돌 복사본: 별개의 Markdown page로 감지되어 파일 트리와 검색 대상에 들어간다. frontmatter/type이 유효하면 그래프 노드가 하나 더 생길 수 있다.
- `raw/sources/**` 아래 허용 확장자 충돌 복사본: 별개의 created source로 인식되어 auto-ingest될 수 있다. 원본과 충돌본의 내용이 다르면 중복/상충 지식 생성 위험이 있다.
- `.llm-wiki/**` 충돌 파일: file watcher가 무시한다. 그러나 review/chat/queue 상태 파일 자체의 Synology 충돌을 앱이 병합하는 로직도 없다.
- 확장자나 위치가 감시 규칙을 통과하지 않으면 앱 화면 갱신/ingest에서 무시될 수 있다.

앱이 “둘 중 하나만 조용히 선택”하는 고유 로직은 없다. Synology가 디스크에 만들어 둔 결과를 일반 파일로 처리할 뿐이다.

### 7.4 실무 판단

현재 코드는 여러 컴퓨터에서 **읽기와 순차적 편집**에는 자동 갱신 편의가 있지만, 동일 파일의 진정한 동시 편집을 안전하게 조정하는 multi-user 시스템은 아니다.

권장 운영 조건은 다음과 같다.

- 같은 raw source를 두 컴퓨터에서 동시에 수정/재인제스트하지 않는다.
- Index/Overview가 갱신되는 ingest는 한 컴퓨터만 담당한다.
- 같은 wiki page 동시 편집을 금지하거나 담당자를 구분한다.
- Synology version history와 conflict 알림을 켠다.
- 충돌 복사본이 생기면 raw source ingest 전에 사람이 먼저 비교·정리한다.

이 권장은 코드의 충돌 방지 기능이 없다는 조사 결과에서 도출한 운영상 완화책이다.

## 8. 예시

### 예시 A — B컴퓨터에서 XLSX 내용 수정

1. Synology가 A컴퓨터의 `raw/sources/상담기록.xlsx`를 갱신
2. A의 watcher가 hash/size 변경을 `modified`로 판정
3. 전체 파일 트리와 dataVersion 갱신
4. autoIngest가 켜져 있으면 수정된 XLSX를 ingest queue에 등록
5. 기존 Entity/Concept와 같은 경로가 생성되면 기존 파일을 읽어 LLM merge

### 예시 B — B컴퓨터에서 Entity 직접 수정

1. `wiki/entities/거래처-a.md` 변경이 A로 동기화
2. watcher가 `.md` modified task로 감지
3. A의 트리·열린 문서·그래프가 갱신
4. raw source가 아니므로 자동 재인제스트는 하지 않음

### 예시 C — 양쪽에서 같은 Entity 편집

1. A와 B가 각자 메모리의 내용을 편집
2. 양쪽 editor가 1초 debounce 후 같은 상대 경로에 저장
3. 앱 간 공유 lock이나 revision 검사가 없음
4. Synology가 한쪽을 최종본으로 정하거나 충돌 복사본을 생성
5. 각 앱은 그 디스크 결과를 일반 modified/created 파일로 처리

## 9. 코드상 확인 한계 및 재현 테스트 상태

- Synology Drive가 특정 OS/버전/설정에서 실제 충돌 파일에 붙이는 정확한 이름과 winner 선정 규칙은 이 저장소 코드의 범위 밖이므로 **코드상 확인 불가**다.
- 두 대의 실제 컴퓨터와 동일 Synology 공유 폴더가 이 조사 환경에 제공되지 않아, 요구한 실제 A/B 동시 수정 재현 테스트는 수행하지 못했다.
- 따라서 충돌 파일의 실제 명명 예, 동기화 지연 시간, Synology UI 알림 결과는 별도 2-PC 재현 테스트가 필요하다.

## 11. 사후 분석 — C(Windows) Review 화면 누락 사건

### 11.1 사건 요약

A(Mac)와 C(Windows)가 NAS 공유 폴더 `성장전략실/Wiki_시장`을 동기화하는 상황에서 A와 NAS에는 `.llm-wiki/review.json`이 존재하지만 C 로컬에는 없었고, C의 Review 화면이 빈 상태로 표시됐다.

이번 분석은 다음 증거를 사용했다.

- A 로컬 파일·심볼릭 링크·inode 확인
- A의 LLM Wiki `app-state.json`
- Synology Drive Client `sys.sqlite`, `filter.sqlite`, `history.sqlite`
- Synology Drive Client 로그
- LLM Wiki의 Review load/save 및 project watcher 코드
- NAS File Station에서 `review.json` 786.7KB 존재 확인이라는 사용자 제공 사실

### 11.2 경로 불일치 조사 결과

두 경로는 **같은 폴더**다.

```text
/Users/zart/Documents/daesan-blog-wiki/daesan-wiki-sync
  → symbolic link
  → /Users/zart/Library/CloudStorage/SynologyDrive-daesan-wiki-sync
```

검증 결과:

- Documents 경로는 길이 63의 symbolic link다.
- `realpath`는 CloudStorage 경로를 반환한다.
- `stat -L`로 따라간 Documents 경로와 CloudStorage 실제 디렉터리의 device와 inode가 모두 동일했다.
- Synology `session_table`에는 session 1개만 있다.
- 해당 session의 실제 `sync_folder`는 CloudStorage 경로이고 `symbolic_link_path`가 Documents 경로다.
- NAS 원격 경로는 share `성장전략실`, `remote_path=/Wiki_시장/`다.
- session status는 1, error는 0이다.

따라서 이 두 표시는 “서로 다른 두 동기화 작업”이 아니다. macOS On-demand Sync가 CloudStorage 실경로와 사용자가 보기 쉬운 symbolic link를 함께 제공한 것이다. **중복 동기화 작업은 이번 문제의 원인이 아니다.**

### 11.3 LLM Wiki가 실제로 연 경로

A의 로컬 앱 설정 파일은 다음 값을 기록하고 있다.

```text
lastProject.path = /Users/zart/Documents/daesan-blog-wiki/daesan-wiki-sync
lastProject.id   = 8831a625-bb3d-4162-8668-4b0171d64597
```

즉 앱은 Documents symbolic link 경로로 프로젝트를 열고 있다. 그러나 이 링크가 CloudStorage 실경로의 같은 inode를 가리키므로 다른 복사본을 연 것은 아니다. 프로젝트의 `.llm-wiki/project.json` ID도 앱의 lastProject ID와 일치한다.

주의: NAS의 `/Wiki_시장/`은 Synology session의 remote root이고, 로컬에서는 `SynologyDrive-daesan-wiki-sync` 자체에 매핑된다. 로컬 경로 뒤에 `Wiki_시장` 하위 폴더를 한 번 더 붙이는 구조가 아니다.

### 11.4 Mac 동기화 작업 설정

Synology 설정 DB에서 다음이 확인됐다.

| 설정 | 값 | 의미 |
|---|---:|---|
| session 수 | 1 | 중복 작업 없음 |
| `is_mac_on_demand_sync_enable` | 1 | Mac 작업은 On-demand Sync |
| `is_selective_sync_enable` | 0 | Mac 폴더 선택 동기화 비활성 |
| `is_file_filter_enable` | 0 | 사용자 파일 필터 비활성 |
| filter row | `.tmp` | 임시 확장자 제외만 존재 |
| session error | 0 | 세션 오류 상태 아님 |

따라서 A 설정에는 `review.json`, JSON, 숨김 폴더 `.llm-wiki`, `lancedb`, `page-history`를 골라 제외하는 규칙이 없다.

Synology client history에도 A의 `review.json`, `ingest-queue.json`, `dedup-queue.json`, `lint.json` 처리가 `is_not_synced=0`, `not_synced_reason=0`으로 기록됐다. 사용자 확인대로 NAS에 `review.json`이 존재하므로 A→NAS 업로드는 성공한 것으로 확정한다.

### 11.5 특정 파일만 누락된 원인 후보 검증

#### 파일 크기

원인으로 볼 수 없다.

- 누락된 `review.json`: 805,587 bytes
- 누락된 `lint.json`, `ingest-queue.json`, `dedup-queue.json`: 각각 2 bytes
- C에 존재한 `file-snapshot.json`: A 기준 269,297 bytes

큰 파일과 2-byte 파일이 함께 누락됐고 더 큰 대조 파일 일부는 동기화됐다. 일관된 크기 임계값 패턴이 아니다.

#### 파일명 또는 디렉터리 여부

현재 증거로 원인으로 볼 수 없다.

- 누락군과 정상군 모두 `.json`이다.
- `chats/`는 C에 존재하지만 `page-history/`, `lancedb/`는 없으므로 “하위 디렉터리는 전부 제외”도 아니다.
- A의 Synology filter DB에는 `.tmp` 외 해당 이름 패턴이 없다.

단, C 자체의 `Sync Rules`, NAS Admin Console의 User Sync Profile은 A에서 읽을 수 없으므로 **C/NAS 측 필터 존재 여부는 별도 확인이 필요**하다.

#### POSIX 권한

최초 업로드 실패 가능성은 있었지만 현재 사건의 지속 원인으로는 배제된다.

- `chmod 644` 후 A가 파일을 읽고 NAS에도 업로드했다.
- NAS에 실제 `review.json`이 존재하므로 A의 로컬 읽기 권한은 C 다운로드 부재를 더 이상 설명하지 못한다.
- 누락군의 현재 권한은 644이며, 누락된 2-byte 파일도 동일하다.

“한 번 권한 오류가 나면 영구 제외 목록에 남는다”는 상태나 목록은 A의 Synology DB와 로그에서 발견되지 않았다. C의 client DB는 조사하지 못했으므로 C 내부 retry 상태까지는 코드상 확인 불가다.

### 11.6 확정된 직접 Root Cause와 미확정된 상위 원인

#### C Review 화면이 빈 직접 원인 — 확정

LLM Wiki의 `loadReviewItems()`는 프로젝트를 열 때 다음 경로를 한 번 읽는다.

```text
{project}/.llm-wiki/review.json
```

파일 부재, online placeholder 읽기 실패, JSON 오류를 모두 catch하여 오류 표시 없이 빈 배열 `[]`을 반환한다. 프로젝트 open 시 `savedReview.length > 0`일 때만 Review store에 넣는다.

또한 file watcher의 `should_watch_rel()`은 `.llm-wiki/**`를 명시적으로 제외한다. 따라서 프로젝트를 연 뒤 `review.json`이 C에 늦게 다운로드되어도:

- Review store 자동 reload 없음
- `dataVersion` 갱신 없음
- Review 화면 자동 복구 없음

즉 **C 로컬에 파일이 없던 순간 앱을 열었고, 앱의 silent-empty + one-shot load 구조 때문에 Review가 빈 화면으로 고정된 것**이 직접 원인이다. 파일이 도착한 뒤에는 프로젝트를 닫았다 다시 열거나 앱을 재시작해야 현재 코드가 읽는다.

추가 위험: 빈 Review store 상태에서 항목 조작이나 프로젝트 전환/종료 flush가 실행되면 C가 빈 배열을 `review.json`으로 저장해 NAS의 정상 파일을 덮어쓸 수 있다. C에서 정상 파일 확인 전 Review 조작을 중지해야 한다.

코드 근거: `src/lib/persist.ts`, `src/App.tsx`, `src/lib/auto-save.ts`, `src-tauri/src/commands/file_sync.rs`.

#### NAS→C 다운로드가 누락된 상위 원인 — 아직 미확정

NAS에는 파일이 있고 A의 upload 성공도 확인됐지만, C의 로컬 Synology DB·Sync Rules·로그를 이 조사 환경에서 읽지 못했다. 따라서 다음 중 어느 하나인지 현재 확정할 수 없다.

1. C 작업이 On-demand이며 `.llm-wiki` placeholder metadata 반영이 정체됨
2. C의 Folder-Based Selective Sync에서 `.llm-wiki` 또는 일부 하위가 제외됨
3. C의 File Filter 또는 NAS User Sync Profile 규칙
4. C Drive Client의 stale index/download queue
5. Windows의 unsupported attribute, path, antivirus/lock 오류

단순 On-demand의 정상 동작이라면 일반적으로 online-only 파일도 이름과 크기 placeholder는 보여야 한다. `dir /a`에도 항목 자체가 전혀 없었다는 사실은 “정상적인 online-only 상태”만으로 충분히 설명되지 않는다. **C 측 선택 동기화/필터/클라이언트 인덱스 상태를 함께 확인해야 한다.**

### 11.7 On-demand와 LLM Wiki의 호환성 판단

Mac session은 On-demand가 확실하다. Synology 공식 문서상 online-only 파일은 열 때 다운로드되며, 폴더를 우클릭해 `Pin local copy permanently`로 오프라인 고정할 수 있다.

LLM Wiki는 프로젝트 open, 검색, 그래프 생성, ingest 중 많은 파일을 짧은 시간에 재귀 열람한다. File Provider가 각 파일을 투명하게 materialize하면 동작할 수 있지만 다음 문제가 있다.

- 대량 hydration으로 초기 로딩 지연
- read timeout/일시 오류가 빈 데이터 또는 skip으로 처리될 수 있음
- 파일명만 보이고 내용이 아직 없는 시간차
- `.llm-wiki/review.json`처럼 실패를 `[]`로 숨기는 경로
- watcher와 cloud placeholder event의 타이밍 차이

따라서 기술적으로 사용 가능하더라도 LLM Wiki 프로젝트 전체에는 On-demand보다 **전체 로컬 고정**이 안전하다.

공식 참고:

- [Synology — What is On-demand Sync?](https://kb.synology.com/en-me/DSM/tutorial/What_is_On-demand_Sync)
- [Synology — Frequently Asked Questions about On-demand Sync](https://kb.synology.com/en-us/DSM/tutorial/Frequently_Asked_Questions_On_Demand_Sync)
- [Synology — My files won't sync](https://kb.synology.com/DSM/tutorial/Why_are_files_not_synced_between_Synology_Drive_and_Drive_desktop_application)

### 11.8 전체 로컬 보관 설정

#### Mac

가장 안전한 즉시 조치는 Finder에서 Synology Drive 프로젝트 **루트 폴더**를 우클릭하고:

```text
Synology Drive → Pin local copy permanently
```

또는 cloud icon이 있는 항목에 `Download Now`를 사용할 수 있지만, Download Now는 영구 pin이 아니므로 디스크 부족 시 다시 제거될 수 있다.

Synology 공식 문서상 macOS On-demand 작업은 기존 작업에서 일반 sync task로 전환할 수 없다. 완전한 일반 sync task가 필요하면 작업을 삭제하고 On-demand를 선택하지 않은 새 작업을 만들어야 한다.

현재 Mac 로그의 client version은 `4.0.17892`다. Synology의 2026 FAQ는 **macOS 4.0.x에서 On-demand task 삭제 시 다운로드된 로컬 폴더 전체가 제거될 수 있다**고 경고한다. 따라서:

1. 먼저 NAS와 별도 로컬 백업 확인
2. 가능하면 Synology Drive Client 4.1.x 이상 업데이트
3. task 삭제보다 우선 루트 `Pin local copy permanently`
4. 일반 sync task 재생성은 백업 후 수행

순서를 지켜야 한다.

#### Windows C

Synology Drive Client에서:

```text
Sync Tasks
  → 해당 작업 선택
  → Sync Rules
  → Sync Mode
  → Enable On-demand Sync to save disk space 체크 해제
```

또는 Windows Explorer에서 프로젝트 루트를 우클릭해:

```text
Synology Drive → Pin local copy permanently
```

를 선택한다. 전체 다운로드가 완료될 때까지 LLM Wiki를 종료해 두는 것이 안전하다.

Windows에서 On-demand를 해제할 수 있다는 절차는 Synology 공식 FAQ 기준이다.

### 11.9 복구 및 검증 절차

현재 C에 원격 접근할 수 없어 아래 조치는 **실행하지 못했다**. 실제 복구 시 순서대로 수행한다.

#### 1단계 — 쓰기 중지와 백업

1. A와 C의 LLM Wiki 종료
2. NAS File Station에서 `.llm-wiki/review.json` 다운로드 백업
3. 파일 크기와 가능하면 MD5/SHA256 기록
4. Mac Synology Client가 4.0.x이므로 sync task 삭제 금지

#### 2단계 — C 동기화 설정 확인

1. Synology Drive Client → Logs에서 `review.json` 검색
2. Sync Tasks → 해당 task → Sync Rules 확인
3. Folder에서 `.llm-wiki` 포함 여부 확인
4. File Filter에서 `.json`, 숨김 폴더, 최대 크기 규칙 확인
5. NAS Admin Console → Settings → User Sync Profiles에서 C 사용자 적용 규칙 확인
6. On-demand 해제 또는 프로젝트 루트 permanent pin

#### 3단계 — C 로컬 도착 검증

Windows Command Prompt:

```bat
dir /a ".llm-wiki"
for %F in (".llm-wiki\review.json") do @echo %~zF
certutil -hashfile ".llm-wiki\review.json" MD5
```

합격 조건:

- 파일이 실제로 존재
- 크기가 NAS/A와 일치
- hash가 A/NAS 백업과 일치
- online-only cloud 상태가 아니라 locally available/pinned 상태

#### 4단계 — Review 앱 검증

1. `review.json` 도착과 hash 확인 후 C에서 LLM Wiki 실행
2. 기존에 열려 있었다면 앱 재시작 또는 프로젝트 전환 후 재오픈
3. Review 화면 항목 수 확인
4. JSON의 미해결 항목 수와 UI 표시 수 대조
5. C에서 임의 Review resolve는 백업 후 1건만 시험
6. NAS와 A에 변경 내용이 정상 반영되는지 확인

파일만 도착시킨 채 이미 열린 Review 화면을 보는 것은 검증이 아니다. 현재 구현은 `.llm-wiki`를 live reload하지 않으므로 반드시 재오픈해야 한다.

### 11.10 향후 다중 컴퓨터 확장 사전 체크리스트

#### 경로와 동기화 작업

- [ ] 각 컴퓨터의 `realpath`/실제 경로 기록
- [ ] 표시 경로가 symbolic link인지 확인
- [ ] Synology Drive Client session/task가 NAS 폴더당 1개인지 확인
- [ ] 같은 NAS remote folder에 중복 task를 만들지 않음
- [ ] LLM Wiki `lastProject.path`가 의도한 task 내부인지 확인
- [ ] `.llm-wiki/project.json`의 project ID가 모든 컴퓨터에서 동일한지 확인

#### 로컬 보관

- [ ] 프로젝트 루트를 `Pin local copy permanently`
- [ ] Windows On-demand를 끄거나 전체 pin
- [ ] Mac은 On-demand task 변환 불가를 인지
- [ ] Mac 4.0.x에서는 업데이트·백업 전 task 삭제 금지
- [ ] `wiki/`, `raw/sources/`, `.llm-wiki/` 모두 로컬 다운로드됐는지 확인

#### 필터와 권한

- [ ] Sync Rules → Folder에 `.llm-wiki` 포함
- [ ] File Filter에 `.json`, `.md`, 숨김 폴더 제외가 없는지 확인
- [ ] NAS User Sync Profile 확인
- [ ] Mac `ls -la`, Windows `dir /a`로 숨김 폴더 확인
- [ ] 현재 사용자에게 읽기/쓰기 권한 부여
- [ ] Windows unsupported attribute와 antivirus 차단 확인

#### 데이터 무결성

- [ ] `review.json` 크기와 hash를 컴퓨터별 비교
- [ ] `ingest-queue.json`, `dedup-queue.json`, `lint.json` 존재 확인
- [ ] `page-history/`, `lancedb/`, `chats/` 목록 비교
- [ ] NAS version history 활성화
- [ ] 한 컴퓨터에서만 ingest 실행
- [ ] 동기화 완료 전 다른 컴퓨터에서 Review/ingest 조작 금지

#### 앱 동작

- [ ] `.llm-wiki` 상태 파일이 도착한 뒤 앱/프로젝트 재오픈
- [ ] Review 화면과 JSON 항목 수 대조
- [ ] 빈 Review 화면을 “리뷰가 없음”으로 바로 판단하지 않음
- [ ] C 로컬 파일 부재 상태에서 앱 종료/프로젝트 전환으로 빈 JSON을 저장하지 않도록 주의

### 11.11 최종 판정

| 가설 | 판정 |
|---|---|
| Documents와 CloudStorage가 별도 복사본 | 기각 — symbolic link와 동일 inode |
| Mac에 중복 sync task 존재 | 기각 — session 1개 |
| A→NAS 업로드 실패 | 기각 — NAS 파일 존재, A history 정상 |
| 805KB 크기 제한 | 기각 — 2-byte 파일도 누락, 더 큰/유사 파일 정상 |
| 파일명/하위 폴더 일괄 제외 | 기각 — 대조군과 A filter 설정 불일치 |
| chmod 전 권한이 현재 지속 원인 | 기각 — NAS 업로드 완료 후 C 부재를 설명 못함 |
| C Review가 빈 앱 직접 원인 | 확정 — 파일 부재를 `[]`로 처리하고 one-shot load |
| NAS→C 누락의 정확한 Client 원인 | 미확정 — C의 DB/로그/Sync Rules 필요 |
| On-demand가 운영 위험을 증가 | 확정 — Mac 설정 ON, 앱의 대량·즉시 읽기 및 silent fallback과 부적합 |
