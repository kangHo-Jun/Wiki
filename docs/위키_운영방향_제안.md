# 대산 위키 운영 방향 (v1, 2026-11-20, 적대적 검증 반영, 미실행)

v0 초안을 독립 에이전트가 반박 검증했고, 그중 핵심 주장은 직접 다시 확인했다. 아래에서 [확인]은 증거를 직접 봤다는 뜻이고, [추정]은 아직 검증하지 않았다는 뜻이다.

## 1. 진단 (확정)

- [확인] **검색 지연의 원인**: 위키가 Synology On-demand 폴더에 있고 디스크가 99% 차서, 파일 내용이 로컬에서 계속 비워진다.
  - 비워진 파일을 처음 읽으면 **0.31초**, 다시 읽으면 0.01초가 걸린다.
  - 검색은 `wiki/` md 약 7,000개를 매번 읽으므로 한 번에 최대 약 37분이 걸릴 수 있다.
  - 1.2GB 중 로컬에 실제로 남아 있는 것은 29MB뿐이다. 받아도 곧 다시 비워진다.
- [확인] **양방향 동기화가 이미 위키를 오염시켰다**:
  - `wiki/`에 Synology 충돌본(`*_Conflict*.md`)이 **1,011개** 있다(concepts 525, entities 369, sources 117). 모두 검색 대상에 들어가 있다.
  - "다른 PC는 보기만 한다"는 운영 의도와 실제 기록이 다르다. 앱 밖에서 11/5 이후 수정된 파일이 168개라는 보고도 있다[추정, 누가 썼는지 확인 필요].
- [확인] **백업이 없다**: Time Machine 대상이 설정되어 있지 않다(`tmutil: No destinations configured`).
- [확인] **벡터 DB(590MB)도 NAS와 양방향 동기화 중이다**: 여러 조각 파일로 된 DB라, 동기화 도중에 버전이 반쪽만 맞는 상태로 손상될 위험이 있다.
  - 앱은 내부 상태 폴더(`.llm-wiki`) 위치를 프로젝트 밖으로 뺄 수 없다(`vectorstore.rs:47`).
  - 따라서 **프로젝트 자체를 로컬로 옮기는 것이 맞다**. 고정("다운로드된 상태로 유지")은 이동 전까지 쓰는 임시 처방일 뿐이다.

## 2. 원칙: 데이터 세 구역 (v0 유지)

| 구분 | 무엇 | 기준 위치 | NAS와의 관계 |
|---|---|---|---|
| A. 입력 | `raw/sources` | NAS가 받은 편지함 + 로컬 사본 | NAS→로컬 pull, 앱으로 가져온 소스는 로컬→NAS push. **둘 다 삭제는 전파하지 않음** |
| B. 산출물 | `wiki/`, 루트 md 3개 | **이 Mac** | 로컬→NAS 게시. 다른 PC는 읽기만 |
| C. 기계 상태 | `.llm-wiki/` | **이 Mac 전용** | 동기화하지 않음. 백업만 함 |

## 3. 실행 순서 (v1)

0. **[즉시, 임시] 증상 완화**: Finder에서 Synology 위키 폴더에 "다운로드된 상태로 유지"를 켠다. 단, 디스크 공간이 있어야 효과가 있다.
1. **디스크 확보 (사용자가 직접)**: 목표는 남은 공간 40GB 이상이다. 큰 파일 목록만 뽑아서 보여 주고, 무엇을 지울지는 사용자가 정한다.
2. **충돌본 정리 결정**:
   - 충돌본 1,011개 목록을 원본과 비교해 보여 주고, 지울지·합칠지를 사용자가 정한다.
   - 이동 전에 정리해야 새 위치로 옮겨 가지 않는다.
   - 11/5 이후 앱 밖에서 수정된 파일 168개가 누구의 수정인지도 확인한다. Claude 작업분인지 다른 PC인지 본다.
3. **멈추기**: 앱 본체, QA 인스턴스, MCP node 프로세스를 모두 종료한다. 인제스트 큐가 비어 있는지 확인한다(현재 비어 있음).
4. **복사**:
   - Synology 클라이언트에서 "최신" 상태인지 확인한다.
   - **NAS SMB 공유에서 `~/LLMWiki/daesan-wiki-sync`로 바로 복사**한다. File Provider를 거치지 않고, 디스크도 한 번만 쓴다.
   - 복사 후 파일 수와 파일별 해시를 비교한다.
   - Synology 폴더에서 `mv`로 빼내지 않는다. 빼내면 NAS에서 삭제로 처리된다.
5. **옛 사본 무력화 (치명 위험 대응)**:
   - Synology 쪽 `.llm-wiki`를 NAS 보관 폴더로 옮겨서, 옛 경로에 `project.json`이 없게 한다.
   - 그렇지 않으면 ID `8831…`가 두 경로에 존재하게 된다. API는 경로 순서로 처음 맞는 것을 고르므로 **옛 경로가 선택된다**(`api_server.rs` 577~641행에서 확인).
   - 앱의 최근 목록에서 옛 항목을 지운다.
   - 끝나면 `projects/current`와 ID 호출이 둘 다 새 경로를 가리키는지 확인한다.
6. **경로 참조 갱신 (push보다 먼저)**:
   - `scripts/`의 `apply_recovery_vectors.py`, `fix_recovery_links.py`, `verify_2nd_knowledge_citations.py`
   - `blogger-duplicate-guard` 스킬의 SKILL.md와 references
   - 문서 3개, `blogger/HANDOFF.md`
   - 과거 `outputs/` 기록은 고치지 않는다.
7. **새 경로로 열기와 재측정**:
   - 프로젝트 ID는 `project.json`에 있으므로 유지된다. 내부 상태는 모두 상대경로라 재임베딩이 필요 없다.
   - 다만 첫 실행 때 11/2 이후 변경분(168개 이상)이 변경 큐에 들어간다. 이동 때문에 생긴 것이 아니다.
   - 목표: 첫 검색 10초 이내.
8. **백업 체계 (Time Machine이 없으므로 새로 만듦)**:
   - 로컬 작업 폴더에 git을 둔다. 텍스트만 추적하고 `.llm-wiki`, `wiki/media`, 바이너리, `*_Conflict*`는 제외한다.
   - NAS **SMB 공유**(Synology Drive 폴더가 아닌 곳)에 bare repo나 `git bundle`을 둔다.
   - `.llm-wiki`는 주 1회 tar로 압축해 NAS 보관 폴더에 둔다.
9. **동기화 스크립트 `wiki_sync.sh`** (macOS 기본 rsync는 openrsync이고 2.6.9 호환):
   - **pull-sources**:
     - 형식: `rsync -rlt -W -i` + `.cache/`, `.DS_Store`, `*_Conflict*` 제외 + `--exclude-from=삭제목록`(앱에서 지운 소스가 다시 살아나지 않게)
     - `--update`와 `--delete`는 쓰지 않는다.
   - **push-sources**: 앱으로 가져온 소스를 NAS에 올린다. `--delete`는 쓰지 않는다.
   - **push-wiki**:
     - 형식: `rsync -rlt -W -i` + `.llm-wiki`, `raw`, `_snapshot*`, `*_Conflict*` 제외
     - 처음 몇 주는 `--delete` 없이 `--backup-dir`을 쓴다. 안정되면 `--delete --max-delete=N`으로 바꾼다.
     - dry-run에서 "목적지가 더 새로운" 파일이 하나라도 있으면 멈춘다. 다른 PC가 수정했다는 신호다.
   - `-c`(체크섬 비교)는 쓰지 않는다. 비워진 파일을 전부 다시 받아오게 된다.
   - [추정] File Provider가 업로드 뒤 수정 시각을 바꿔서 매번 전체를 다시 보낼 수 있다. 처음 실행 2회는 `-i` 출력으로 확인한다.
   - [추정] NAS 쪽으로 동기화할 때 Synology 폴더도 비워진 상태라 쓰기와 비교가 느릴 수 있다. 느리면 Synology Drive 대신 NAS SMB 경로로 바로 보내는 방식으로 바꾼다.
10. **정리**:
    - 죽은 예약 가져오기 설정(`Crawling-source`)을 끄거나 지운다.
    - `_snapshot*`, `_backup*` 폴더는 NAS 보관 폴더로 옮긴다.
11. 그래도 검색이 느리면 그때 앱 코드를 보강한다(키워드 인덱스 캐시, LanceDB ANN 인덱스).

## 4. 일상 운영 (이동 후)

- 인제스트 전: `wiki_sync.sh pull-sources`
- 작업 후: `git commit` → `wiki_sync.sh push-sources push-wiki` → 주 1회 백업
- 주간 점검:
  - 디스크 여유 40GB 이상
  - 로컬 작업 폴더에 `dataless`나 `*_Conflict*` 파일이 0개인지
  - `probe_search_latency.sh`
  - `verify_2nd_knowledge_citations.py`

## 5. v0에서 바뀐 점

- 옛 사본의 `project.json`을 제거하는 단계를 추가했다(치명).
- 충돌본 1,011개를 정리하고 "보기만 한다" 전제를 다시 확인하는 단계를 추가했다.
- 경로 갱신을 push보다 앞으로 옮겼다.
- 소스 삭제 목록과 소스 push를 추가했고, `--update`를 뺐다.
- Time Machine을 전제하던 부분을 지우고, NAS SMB에 git bundle과 tar를 두는 방식으로 바꿨다.
- 복사 경로를 File Provider에서 NAS SMB 직접 복사로 바꿨다.
- rsync 옵션을 openrsync에 맞게 고쳤다.
- 원인 확정 시험 결과(파일당 0.31초)를 추가했다.
